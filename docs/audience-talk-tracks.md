# 三类观众的不同讲法

共同前提：先说业务结果，明确全部是模拟数据；不从 OMA、多 Agent 或技术架构讲起。

## 面对老板 / 创始人

### 30 秒开场

> 这不是一个自动下单系统，而是把 BOM 报价团队每天散落在 Excel、邮件和微信式回复里的整理工作，先变成一份负责人能审的采购稿。您先看结果：哪些有报价、哪些不能报、最低价为什么没选、风险在哪里、谁要确认，一页看清。全部是模拟数据，真实价值还要用历史 BOM 回放验证。

### 重点展示

- 91.7% 的演示覆盖率定义，而不是泛泛说“高覆盖”；
- 最低价不一定推荐，避免只比价格；
- 负责人审批和异常清单；
- 不接生产系统也能先做历史回放。

### 只谈这三个经营问题

1. 报价速度是否真的影响成交或客户体验？
2. 错料、过期价和低毛利是否造成过实际损失？
3. 这个问题是否值得一个明确 owner 和试点预算？

### 不要说

- “AI 可以替代采购”；
- “已经提升成交/毛利”；
- “先部署全套平台”。

## 面对采购 / BOM 报价负责人

### 30 秒开场

> 您不用先告诉我内部流程。我先用模拟数据给您看一份审核稿：原 BOM 行如何合并、四家回复怎么统一口径、推荐为什么不是最低价、哪里需要采购或工程确认。您只需要判断这个结果像不像一份能工作的采购稿。

### 重点展示

- 原 BOM 行号和归一化记录；
- 库存、MOQ、交期、有效期、Date Code、渠道和资质；
- 替代料必须工程确认；
- 原始证据文件和位置；
- 改选、补询、审批备注和审计记录。

### 只谈这三个流程问题

1. 现在逐行整理最耗时的是哪一步？
2. 哪些判断资深采购一定要保留？
3. 最常见、代价最高的错报是什么？

### 不要说

- “系统自动判断一定比人准”；
- “接上邮箱就能全自动”；
- “推荐结果可以直接下单”。

## 面对技术负责人

### 30 秒开场

> 主路径是本地 React/TypeScript 应用通过 Node 服务真实调用 OMA 和 DeepSeek，但只发送明确标记的模拟数据。模型做多格式抽取和证据复核，业务规则、人工审批和导出留在应用侧。Key 只在服务端环境变量里；当前没有接任何真实业务系统。

### 重点展示

- `@open-multi-agent/core@1.12.1` 作为 npm 依赖，仓库本身没有被修改；
- 固定 `runTasks()` DAG：5 个前置任务并行，1 个独立复核任务依赖汇总；
- 输出 schema、连续原文证据、料号、价格、置信度和未解决字段校验；
- 解析、业务规则和导出是 TypeScript；
- 固定汇率、税率、日期和毛利阈值明示；
- 浏览器只能访问同源 `/api`，服务端除模型 provider 外无其他外联；
- 实时失败不自动降级；离线回放有独立 execution mode 与 replay id；
- 状态仅在当前浏览器内存，刷新即可重置；
- 模型输出不能绕过确定性约束和人工审批。

### 只谈这三个技术问题

1. 历史数据能否在客户边界内脱敏回放？
2. 真实系统的权威字段、更新频率和写入边界是什么？
3. 哪些动作必须保持只读、人工确认或完全禁止？

### 对方追问 OMA 为什么必要

> 这里不是为了展示多个 Agent，而是把五个可以独立读取的输入并行处理，再让独立角色只做证据复核。真实执行由 OMA 负责调度、依赖和 trace；“最低价能不能选、是否过期、是否低于 MOQ”仍是应用规则。离线回放只是备用演示路径，不等于实时 OMA。

### 没有 Key 时怎么说

> 代码和 OMA 调度结构已经通过无网络 fixture adapter 测试；但没有真实 provider 凭证时，我不会说 DeepSeek E2E 已经通过。当前只能展示明确标注的离线回放。
